# s21: Agent Evaluation

前面的章节一直在回答一个问题：

> **怎样构建一个更有能力的 Agent Harness？**

从最开始的 Agent Loop，到 Tool Use、Todo、Subagent、Skill、Context Compact、Permission、Memory、Error Recovery、Task、Background Task、Agent Team、Worktree、MCP，再到上一章对 Tool System 的整理，我们不断给 Agent 增加新的能力。

但当 Agent 能做越来越多事情后，会出现另一个问题：

> **我们怎么知道它真的做对了？**

比如：

* Agent 最后说“任务已经完成”，它真的完成了吗？
* 修改了 system prompt 后，效果是真的更好，还是只是这一次碰巧成功？
* Agent 得到了正确答案，但其实只是猜中的，这算成功吗？
* 两个 Agent 最后都让测试通过，但其中一个偷偷删除了测试，它们应该得到一样的评价吗？
* 一个自然语言回答没有唯一标准答案，又该怎么自动判断质量？

这些问题都属于：

**Agent Evaluation。**

这一章第一次不再继续给 Agent 增加能力，而是站到 Agent 外面，观察并评价它。

---

## 目标

`s21` 的目标不是实现一个完整的 benchmark 平台，也不是完整复现 SWE-bench、GAIA 或 τ²-bench。

这一章只做一件更小的事：

> **用最少的代码，把 Agent Evaluation 的完整闭环跑通。**

我们会实现三个简单的 Eval Case，分别展示：

1. 如何定义一个评估任务。
2. 如何准备一个可重复的 Environment。
3. 如何运行 Agent，并记录可观察的执行过程。
4. 如何使用确定性 Assertion 判断任务是否成功。
5. 如何检查 Agent 的 Tool Trajectory。
6. 当结果无法通过程序直接判断时，如何使用 LLM-as-a-Judge。

最终流程是：

```text
Eval Case
   |
   v
Prepare Environment
   |
   v
Run Agent
   |
   v
Agent Run
   |
   +--------------------+
   |                    |
   v                    v
Assertion Evaluator   LLM Judge
   |                    |
   +---------+----------+
             |
             v
         Eval Result
```

这就是这一章最重要的结构。

# 从 s20 开始，而不是从 sfull 开始

这一章直接从上一章：

```text
s20_tool_refactor
```

继续演进。

`s20` 已经有了一个足够完整但仍然很小的 Agent：

```text
Agent

├── ToolContext
└── ToolRouter
```

以及本章评估任务需要的基本工具：

```text
bash
read_file
write_file
edit_file
```

这正好适合作为 Evaluation 的被测对象。

本章不会直接使用完整的：

```text
sfull
```

因为 `sfull` 已经包含：

```text
permission
compact
recovery
memory
skill
task
background
team
worktree

...
```

如果一开始就在这样一个复杂 Agent 上讲 Evaluation，当任务失败时，很难看清：

```text
是模型的问题？

是工具的问题？

是 compact？

是 recovery？

是 permission？

还是 evaluator 本身的问题？
```

这一章真正想让读者理解的是 Evaluation，而不是重新分析整个 Harness。

所以本章遵循一个原则：

> **被评估的 Agent 尽量简单，Evaluation 的结构尽量清楚。**

# 本章不会重新实现 Agent

`s21` 不会重新设计一套新的 Agent。

它只是从 `s20` 的 Agent 上做两个很小的改造：

```text
s20 Agent
   |
   +-- 增加 Agent::run()
   |
   +-- 记录 AgentRun
   |
   v
s21 Agent
```

也就是说，本章新增的重点并不在 Agent 内部。

重点是在 Agent 外面增加：

```text
EvalCase
EvalRunner
Evaluator
EvalResult
```

这也是一个重要边界：

> **Agent 负责完成任务，Evaluation Harness 负责判断任务完成得怎么样。**

# 为什么普通测试还不够

Rust 项目里我们已经很熟悉这种测试：

```rust
#[test]
fn test_add() {
    assert_eq!(add(1, 2), 3);
}
```

它的执行过程非常稳定：

```text
固定输入
  ->
执行固定函数
  ->
固定输出
  ->
assert_eq!
```

但是 Agent 不一样。

假设给 Agent 一个任务：

```text
修复这个 Rust 项目中的 bug。
```

第一次运行，它可能：

```text
read_file
  ->
edit_file
  ->
bash cargo test
  ->
final answer
```

第二次可能：

```text
bash cargo test
  ->
read_file
  ->
edit_file
  ->
bash cargo test
  ->
final answer
```

甚至第三次：

```text
read_file
  ->
read_file
  ->
edit_file
  ->
edit_file
  ->
bash cargo test
```

这些执行路径并不一样。

但它们都可能正确。

所以我们不能简单要求：

```rust
assert_eq!(
    actual_actions,
    expected_actions
);
```

Agent Evaluation 更关心的是：

```text
任务最终有没有完成？

环境最终是不是正确的？

有没有发生不允许的行为？

回答质量是否满足要求？
```

因此 Agent Evaluation 测试的不是某个固定函数。

它测试的是：

```text
Model
+
Prompt
+
Tools
+
Harness
+
Environment
```

组成的整个 Agent 系统。

---

# Evaluation 的对象是什么

这是理解 Agent Evaluation 最重要的一点之一。

我们经常说：

```text
评估某个模型
```

但对于 Agent 来说，更准确的对象应该是：

```text
Agent = Model + Harness
```

比如同一个模型：

```text
Model A
```

放在只有：

```text
bash
```

的 Agent Harness 中，和放在拥有：

```text
read_file
edit_file
permission
compact
recovery
skills
```

的 Harness 中，完成真实任务的能力可能完全不同。

所以本章不是简单：

```text
Prompt
  ->
Model
  ->
Score
```

而是：

```text
Eval Case
   |
   v
Agent
(Model + Harness)
   |
   v
Agent Run
   |
   v
Evaluation
```

评估的是整个 Agent。

---

# Evaluation Harness 在 Agent 外面

这一章增加的 Evaluation Harness 不属于 Agent 本身。

它站在 Agent 外部。

可以把两者想象成：

```text
+----------------------------------+
|        Evaluation Harness        |
|                                  |
|  prepare environment             |
|          |                       |
|          v                       |
|      +-------+                   |
|      | Agent |                   |
|      +---+---+                   |
|          |                       |
|          v                       |
|      Agent Run                   |
|          |                       |
|          v                       |
|      Evaluator                   |
|          |                       |
|          v                       |
|      Eval Result                 |
+----------------------------------+
```

Agent 自己不知道：

```text
我现在正在参加 benchmark
```

对 Agent 来说，它只是像平常一样收到一个任务：

```text
Fix the bug in this Rust project.
```

然后使用工具完成任务。

这也是比较理想的 Evaluation 结构。

Evaluator 不应该偷偷：

```text
帮助 Agent 找到答案
```

它只是：

```text
准备环境
运行 Agent
观察结果
评分
```

# 一个 Eval Case 到底是什么

刚开始接触 benchmark 时，很容易把 Eval Case 理解成：

```text
一个问题
+
一个标准答案
```

比如：

```text
Question:
1 + 1 = ?

Expected:
2
```

这种形式适合简单问答。

但 Agent 通常不仅回答问题，它还会操作环境。

例如：

```text
修复 calculator 项目中的除零错误。
```

那么一个完整 Eval Case 至少包含：

```text
Task
+
Environment
+
Evaluation Criteria
```

也就是三个问题：

```text
Agent 要完成什么？

Agent 从什么状态开始？

什么样才算成功？
```

在这一章中，我们只需要一个非常简单的结构：

```rust
pub struct EvalCase {
    pub name: String,
    pub prompt: String,
    pub fixture: Option<PathBuf>,
    pub evaluator: Evaluator,
}
```

没有设计复杂 Dataset Schema。

因为这一章真正重要的是概念：

```text
Task
+
Environment
+
Evaluation
```

而不是 benchmark 文件格式。

---

# Task：Agent 要完成什么

`prompt` 就是发给 Agent 的任务。

例如：

```text
The calculator crate crashes when dividing by zero.

Fix the bug without changing the public function signature.
Run the tests before finishing.
```

它和正常用户输入没有本质区别。

正常使用 Agent：

```text
User
  ->
Agent
  ->
User 判断结果
```

Evaluation 中：

```text
EvalRunner
  ->
Agent
  ->
Evaluator 判断结果
```

EvalRunner 可以理解成：

> **一个能够重复给 Agent 同样任务的自动用户。**

---

# Environment：Agent 从哪里开始

只有 Task 还不够。

假设第一次运行：

```text
修复 src/lib.rs 中的 bug
```

Agent 把 bug 修好了。

如果第二次继续使用这个目录：

```text
bug 已经不存在了
```

那么第二次评估和第一次评估就不再是同一个任务。

因此每一次运行之前，我们都需要把 Environment 恢复到相同的初始状态。

这一章使用最简单的方式：

**Fixture。**

例如：

```text
fixtures/
├── bug_fix/
│   ├── Cargo.toml
│   ├── src/
│   │   └── lib.rs
│   └── tests/
│       └── calculator.rs
│
└── file_lookup/
    ├── README.md
    ├── config.toml
    └── data.json
```

运行时：

```text
fixture
   |
   | copy
   v
temporary workspace
   |
   v
Agent
```

第一次：

```text
fixtures/bug_fix
       |
       v
/tmp/s21_eval/bug_fix/run-001
```

第二次：

```text
fixtures/bug_fix
       |
       v
/tmp/s21_eval/bug_fix/run-002
```

每次都从同一个 fixture 重新复制。

这样 Agent 每次看到的初始状态相同。

这叫：

**Environment Reset。**

这里的临时 workspace 用于保证每个 Case 都从重新复制的 fixture 开始，它不是安全 sandbox。`read_file`、`write_file` 和 `edit_file` 会检查路径是否位于 `ToolContext.work_dir`；`bash` 只把这个目录设为 working directory，仍可能访问宿主系统允许访问的其他路径。本章没有实现 Docker、容器或 OS 级隔离。

---

# Tools：Agent 能对 Environment 做什么

Environment 定义：

```text
Agent 能看到什么
```

Tools 定义：

```text
Agent 能做什么
```

本章直接复用 `s20` 的基本工具：

```text
bash
read_file
write_file
edit_file
```

比如：

```text
                Environment
                    ^
                    |
         read_file / bash
                    |
                  Agent
                    |
       write_file / edit_file
                    |
                    v
                Environment
```

本章不会重新实现 Tool System。

这部分已经在前面的章节讲过。

Evaluation Harness 只是使用现有 Agent：

```text
prepare environment
       |
       v
create ToolContext(work_dir)
       |
       v
run Agent
```

所以 Evaluation 和 Tool System 是两个独立层次。

# 三个 Case 使用同一个 Agent

这一章有三个 Eval Case。

它们不会分别创建三个不同能力的 Agent。

三个 Case 使用完全相同的 Agent：

```text
                  Agent
                    |
       +------------+------------+
       |            |            |
       v            v            v
    bug_fix     file_lookup   rust_explain
```

同样的：

```text
Model
System Prompt
ToolRouter
Tool Set
```

变化的是：

```text
Task
Environment
Evaluation Criteria
```

这很重要。

因为我们真正要展示的是：

> **同一个 Agent，可以根据任务类型使用不同的评估方法。**

而不是：

```text
不同 Agent 如何完成不同任务
```

# Agent 为什么需要一个可编程入口

`s20` 的 Agent 主要面向 CLI：

```text
User
  ->
Terminal
  ->
Agent Loop
```

但是 Evaluation Harness 不应该模拟用户在 Terminal 中输入。

EvalRunner 应该能够直接：

```rust
agent.run(prompt).await
```

所以本章会给 Agent 增加一个非交互式入口：

```rust
pub async fn run(
    &mut self,
    prompt: impl Into<String>,
) -> anyhow::Result<AgentRun>
```

于是调用关系变成：

```text
           CLI
            |
            v
        Agent::run()
            ^
            |
         EvalRunner
```

CLI 和 Evaluation 不需要维护两套 Agent Loop。

# AgentRun：一次 Agent 执行的结果

以前我们执行 Agent，最关心的是：

```text
最终回答是什么？
```

Evaluation 中还不够。

例如 Agent 最后说：

```text
I fixed the bug and all tests pass.
```

这句话不能证明：

```text
bug 真的修好了
```

也不能证明：

```text
cargo test 真的执行过
```

所以一次 Eval Run 至少记录：

```rust
pub struct AgentRun {
    pub final_answer: String,
    pub tool_calls: Vec<ToolCallRecord>,
}
```

Tool Call：

```rust
pub struct ToolCallRecord {
    pub name: String,
    pub input: serde_json::Value,
    pub output: String,
}
```

例如：

```text
ToolCall
  read_file("src/lib.rs")

ToolCall
  edit_file(...)

ToolCall
  bash("cargo test")

ToolResult
  test result: ok

FinalAnswer
  Fixed the bug and verified it with cargo test.
```

这样 EvalRunner 不仅知道：

```text
Agent 最后说了什么
```

还知道：

```text
Agent 实际做了什么
```

---

# 为什么这里只用 Vec<ToolCallRecord>

真正的生产 Agent 可能会有复杂的 Observability：

```text
Event Bus
Span
Trace
JSONL
Database
OpenTelemetry
```

但这一章完全不需要。

我们只需要：

```rust
Vec<ToolCallRecord>
```

因为本章要解释的是：

> **为什么 Evaluation 需要观察 Agent 的行为。**

而不是：

> **怎样构建一个完整的 Agent Observability 系统。**

保持最小实现，反而更容易理解。

---

# Trajectory 是什么

一次 Agent 执行过程中发生的这些可观察行为，可以称为：

**Trajectory。**

例如：

```text
read_file
  ->
edit_file
  ->
bash
  ->
tool result
  ->
final answer
```

就是一条简单 trajectory。

Trajectory 可以包含：

```text
Assistant Message

Tool Call

Tool Input

Tool Result

Final Answer
```

如果需要，也可以进一步包括：

```text
Environment Change
```

但这一章只记录工具调用和最终回答。

---

# Trajectory 不是什么

Trajectory 不是模型隐藏的思维过程。

我们不需要知道：

```text
模型心里到底是怎么一步步想的
```

Evaluation 只关心可观察行为：

```text
模型说了什么

调用了什么工具

工具参数是什么

工具返回了什么

最后环境是什么

最终回答是什么
```

所以：

```text
Trajectory
=
Observable Behavior
```

而不是：

```text
Trajectory
=
Hidden Chain of Thought
```

这对于 Agent Evaluation 通常已经足够。

---

# Result Evaluation 和 Trajectory Evaluation

有了 AgentRun 后，可以从两个角度评价 Agent。

第一种：

```text
最终结果对不对？
```

例如：

```text
cargo test 是否通过？
```

可以称为：

**Result Evaluation。**

第二种：

```text
Agent 是怎么做到的？
```

例如：

```text
有没有读 data.json？

有没有执行 cargo test？

有没有修改 tests/？

有没有执行危险命令？
```

可以称为：

**Trajectory Evaluation。**

---

## 为什么有时候不能只看结果

假设两个 Agent 都让：

```text
cargo test
```

通过。

Agent A：

```text
修改 src/lib.rs
  ->
cargo test
  ->
PASS
```

Agent B：

```text
删除失败测试
  ->
cargo test
  ->
PASS
```

如果 evaluator 只有：

```text
cargo test == PASS
```

那么两个 Agent 都会得到：

```text
PASS
```

但显然 Agent B 并没有正确完成任务。

所以真实 Evaluation 经常需要：

```text
Final State
+
Trajectory
```

一起看。

# 两种最基本的 Evaluator

这一章只实现两类 Evaluation：

```text
Evaluator
├── Assertion
└── LLM Judge
```

它们对应一个非常简单的问题：

```text
这个成功条件能不能通过程序直接判断？
```

如果可以：

```text
Assertion Evaluator
```

如果不可以：

```text
LLM Judge
```

基本原则：

> **能确定性验证的地方，优先确定性验证。**

---

# Assertion Evaluator

最简单、最可靠的 Evaluation 就是普通程序判断。

例如代码修复任务：

```text
cargo test
```

退出码为：

```text
0
```

表示成功。

Evaluator 可以自己执行：

```rust
let output = Command::new("cargo")
    .arg("test")
    .current_dir(&workspace)
    .output()
    .await?;

let passed = output.status.success();
```

然后返回：

```rust
EvalResult {
    passed,
    score: if passed { 1.0 } else { 0.0 },
    reason: ...,
}
```

这就是一个最简单的 Agent Evaluation。

---

# 不要让 Agent 自己给自己判分

假设 Agent 最后说：

```text
All tests pass.
```

这只是 Agent 的声明。

Evaluation Harness 不应该因此直接：

```text
PASS
```

它应该自己再执行：

```bash
cargo test
```

如果结果：

```text
FAILED
```

那么最终就是：

```text
FAIL
```

所以：

```text
Agent's claim
!=
Evaluation Result
```

Evaluation 的作用之一，就是把：

```text
Agent says it works
```

变成：

```text
We verified it works
```

# Case 1：SWE-bench 风格的代码修复

第一个 Case 模拟一个最小的 SWE-bench 风格任务。

Fixture：

```text
fixtures/bug_fix/
├── Cargo.toml
├── src/
│   └── lib.rs
└── tests/
    └── calculator.rs
```

代码：

```rust
pub fn divide(a: i32, b: i32) -> i32 {
    a / b
}
```

测试：

```rust
#[test]
fn divide_by_zero_returns_zero() {
    assert_eq!(divide(10, 0), 0);
}
```

任务：

```text
The calculator crate crashes when dividing by zero.

Fix the bug without changing the public function signature.
Run the tests before finishing.
```

Agent 可以自由选择路径。

例如：

```text
read_file
  ->
edit_file
  ->
bash cargo test
```

也可能：

```text
bash cargo test
  ->
read_file
  ->
edit_file
  ->
bash cargo test
```

Evaluator 不要求固定轨迹。

最终执行：

```bash
cargo test
```

判断真实 Environment。

流程：

```text
copy fixture
    |
    v
temporary workspace
    |
    v
run Agent
    |
    v
modified workspace
    |
    v
cargo test
    |
    +------ PASS
    |
    +------ FAIL
```

这个 Case 主要展示：

> **通过最终 Environment State 验证 Agent 是否真正完成任务。**

---

# Case 1 还能增加一个过程断言

为了展示 Result 和 Trajectory 的区别，可以再增加一个非常简单的检查：

```text
Agent 是否执行过 cargo test？
```

例如：

```rust
let ran_tests = run.tool_calls.iter().any(|call| {
    call.name == "bash"
        && call.input.to_string().contains("cargo test")
});
```

于是 Case 1 可以同时展示：

```text
Result:
cargo test 最终是否通过

Trajectory:
Agent 自己有没有主动验证
```

但最终环境验证仍然比 Agent 自己执行过测试更重要。

因为即使 trajectory 中出现：

```text
cargo test
```

最后 Environment 仍然可能是失败的。

---

# Case 2：GAIA 风格的工具任务

第二个 Case 不需要修改代码。

Fixture：

```text
fixtures/file_lookup/
├── README.md
├── config.toml
└── data.json
```

`data.json`：

```json
{
  "services": {
    "service-a": {
      "timeout": 30
    },
    "service-b": {
      "timeout": 60
    }
  }
}
```

任务：

```text
What is the timeout configured for service-a?

Find the answer from the files in the workspace.
```

Agent 可能：

```text
read_file("README.md")
  ->
read_file("data.json")
  ->
final answer: 30
```

这里可以检查两件事。

首先：

```text
Final Answer == 30
```

其次：

```text
Trajectory 中读取过 data.json
```

例如：

```rust
let answer_correct =
    run.final_answer.contains("30");

let read_data_file =
    run.tool_calls.iter().any(|call| {
        call.name == "read_file"
            && call.input.to_string().contains("data.json")
    });

let passed =
    answer_correct && read_data_file;
```

这个 Case 展示：

```text
Result Evaluation
+
Trajectory Evaluation
```

---

# 为什么正确答案还不一定够

假设模型没有读取任何文件。

它直接回答：

```text
30
```

而答案碰巧正确。

如果我们的任务只是：

```text
回答 service-a timeout
```

那么也许可以算成功。

但如果我们真正想测试：

> **Agent 能否通过工具从 workspace 获取信息？**

那么：

```text
有没有读取 data.json
```

就是 Evaluation Criteria 的一部分。

因此：

> **Eval Case 测到什么，取决于你定义了什么成功条件。**

不是题目名字决定的。

---

# Initial State、Actions 和 Final State

Agent Task 可以用下面这个模型理解：

```text
Initial State
    |
    v
Agent Actions
    |
    v
Final State
```

Evaluator 可以检查：

```text
Final State
```

也可以检查：

```text
Actions
```

例如：

```text
Task:
删除 temp.txt
```

Final State：

```text
temp.txt 不存在
```

Trajectory：

```text
没有删除其他文件
```

所以一个成功条件可能是：

```text
目标完成
AND
没有产生不允许的副作用
```

这比单纯：

```text
final_answer == expected
```

更接近真实 Agent Evaluation。

---

# Assertion 可以有很多种

Assertion 并不只是：

```text
cargo test
```

它还可以检查：

```text
文件存在吗？

文件内容正确吗？

某个目录有没有被修改？

某条命令退出码是不是 0？

某个 Tool 有没有被调用？

某个 Tool 有没有被禁止调用？

数据库状态是不是正确？

JSON 字段是不是期望值？
```

例如一个代码任务：

```text
cargo test PASS
AND
tests/ 未修改
AND
Cargo.toml 仍然存在
```

只有全部满足：

```text
PASS
```

Evaluation Criteria 可以由多个简单条件组成。

---

# 什么情况下 Assertion 不够

并不是所有任务都有明确的：

```text
cargo test
```

例如：

```text
Explain why this Rust code fails to compile,
and provide a beginner-friendly fix.
```

可能有很多不同但正确的回答。

Answer A：

```text
第一次 mutable borrow 仍然有效，
所以创建第二个 mutable borrow 时发生冲突。
```

Answer B：

```text
两个 &mut borrow 的生命周期发生重叠，
违反了 Rust 对独占可变引用的要求。
```

两种表达不同。

但都可能正确。

这时候不能写：

```rust
assert_eq!(answer, expected_answer);
```

也不能简单：

```rust
answer.contains("borrow")
```

因为错误回答同样可能包含这个词。

这时可以使用：

**LLM-as-a-Judge。**

---

# LLM-as-a-Judge

LLM Judge 的基本过程很简单。

把：

```text
Task
+
Agent Answer
+
Rubric
```

发送给另一个 LLM。

例如：

```text
Task:

Explain why this Rust code fails because of borrowing
and provide a valid fix.

Agent Answer:

...

Rubric:

1. Correctly identifies overlapping mutable borrows.
2. Correctly explains why the borrows conflict.
3. Provides at least one valid fix.
4. Does not invent nonexistent Rust rules.
5. The explanation is understandable to a beginner.
```

Judge 返回：

```json
{
  "passed": true,
  "score": 0.9,
  "reason": "The answer correctly identifies the overlapping mutable borrows and provides a valid fix."
}
```

Evaluation Harness 再解析成：

```rust
EvalResult
```

---

# Rubric 是什么

Rubric 可以理解成：

> **给 Judge 的阅卷标准。**

如果我们只告诉 Judge：

```text
评价这个回答好不好。
```

那么标准非常模糊。

Judge 只能凭整体感觉评价。

更好的 Rubric 是：

```text
1. 是否指出 mutable borrow 冲突
2. 是否解释冲突为什么发生
3. 修复方案是否真的有效
4. 是否包含错误 Rust 规则
5. 是否适合初学者理解
```

这样 Judge 就不再只是：

```text
我觉得这个回答不错
```

而是在做：

```text
逐项检查 Evaluation Criteria
```

所以 LLM Judge 最重要的部分不是复杂 Prompt。

而是：

**清楚的 Rubric。**

---

# Case 3：需要 LLM Judge 的开放任务

第三个 Case 使用一个 Rust borrowing 示例：

```rust
fn main() {
    let mut values = vec![1, 2, 3];

    let first = &mut values[0];
    let second = &mut values[1];

    *first += 1;
    *second += 1;
}
```

任务：

```text
Answer directly from the code shown below.
Do not use tools for this task.

Explain to a Rust beginner why this code fails to compile.

Explain the borrowing problem and provide at least one valid fix.
```

这个任务没有唯一文本答案。

Rubric：

```text
- 必须识别 overlapping mutable borrows。
- 必须说明 Rust 不允许两个重叠的 &mut borrow。
- 必须给出至少一种有效修复方式。
- 不得错误声称 Vec 永远不能同时修改多个元素。
- 解释应该适合 Rust 初学者。
```

执行流程：

```text
Task
  |
  v
Agent
  |
  v
Final Answer
  |
  + Rubric
  |
  v
LLM Judge
  |
  v
score + reason
```

这个 Case 展示：

> **当结果无法通过程序直接判断时，可以使用 Rubric + LLM Judge。**

---

# Assertion 和 LLM Judge 怎么选

一个简单原则：

```text
能不能直接检查真实状态？
        |
   +----+----+
   |         |
  YES        NO
   |         |
   v         v
Assertion   LLM Judge
```

例如：

| Evaluation Criteria | 更适合       |
| ------------------- | --------- |
| `cargo test` 是否通过   | Assertion |
| 文件是否存在              | Assertion |
| JSON 字段是不是 30       | Assertion |
| 是否调用某个 Tool         | Assertion |
| 是否修改受保护目录           | Assertion |
| 数据库状态是否正确           | Assertion |
| 解释是否准确              | LLM Judge |
| 回答是否完整              | LLM Judge |
| 文档是否清晰              | LLM Judge |
| 建议是否合理              | LLM Judge |

如果可以可靠地写：

```rust
if condition {
    pass
}
```

那么就没有必要调用一个 LLM。

所以一般应该：

```text
Deterministic Verification First
```

然后才是：

```text
LLM-as-a-Judge
```

# EvalResult

不管具体使用哪种 Evaluator，最终都返回相同结果：

```rust
pub struct EvalResult {
    pub passed: bool,
    pub score: f32,
    pub reason: String,
}
```

例如 Assertion：

```rust
EvalResult {
    passed: true,
    score: 1.0,
    reason: "cargo test passed".into(),
}
```

或者 Judge：

```rust
EvalResult {
    passed: true,
    score: 0.9,
    reason: "The answer satisfies all essential rubric items.".into(),
}
```

这样 EvalRunner 不需要关心评分细节。

它只知道：

```text
AgentRun
  ->
Evaluator
  ->
EvalResult
```

---

# Evaluator

为了保持这一章简单，可以直接使用 enum：

```rust
pub enum Evaluator {
    Assertion(AssertionEvaluator),
    LlmJudge(LlmJudgeEvaluator),
}
```

执行：

```rust
impl Evaluator {
    pub async fn evaluate(
        &self,
        run: &AgentRun,
        workspace: &Path,
    ) -> anyhow::Result<EvalResult> {
        match self {
            Evaluator::Assertion(evaluator) => {
                evaluator.evaluate(run, workspace).await
            }

            Evaluator::LlmJudge(evaluator) => {
                evaluator.evaluate(run).await
            }
        }
    }
}
```

这里故意不设计复杂的：

```text
Verifier Plugin System
Evaluator Registry
Dynamic Trait Factory
```

因为本章真正要表达的是：

> **同一个 AgentRun 可以通过不同方式评分。**

---

# EvalRunner

EvalRunner 本身应该非常简单。

伪代码：

```rust
pub async fn run_eval(
    case: &EvalCase,
) -> anyhow::Result<EvalResult> {
    let workspace =
        prepare_workspace(case)?;

    let mut agent =
        build_agent(&workspace).await?;

    let run =
        agent.run(&case.prompt).await?;

    let result =
        case.evaluator
            .evaluate(&run, &workspace)
            .await?;

    Ok(result)
}
```

整个流程其实就是：

```text
prepare
  ->
run
  ->
evaluate
```

如果用普通测试语言表达，就是：

```text
Arrange
  ->
Act
  ->
Assert
```

只是这里：

```text
Act
```

不再是调用一个普通函数。

而是运行一个完整 Agent。

---

# Agent 和 EvalRunner 的职责边界

本章应该保持这个边界：

```text
EvalRunner
├── 准备 workspace
├── 创建 Agent
├── 给 Agent 任务
├── 获取 AgentRun
└── 调用 Evaluator

Agent
├── 接收任务
├── 调用 Tool
├── 修改 Environment
├── 生成 Final Answer
└── 返回 AgentRun
```

Agent 不负责：

```text
给自己评分
```

Evaluator 也不负责：

```text
帮助 Agent 完成任务
```

两边职责分开。

# Evaluation Criteria 才真正定义了任务

假设两个 Eval Case 使用完全相同的 Prompt：

```text
Find the timeout of service-a.
```

Evaluator A：

```text
Final Answer == 30
```

Evaluator B：

```text
Final Answer == 30
AND
read_file("data.json") happened
```

这实际上是两个不同的评估任务。

因为：

```text
什么叫成功
```

不一样。

所以设计 Evaluation 时，真正重要的不只是：

```text
Task 怎么写
```

更重要的是：

```text
Evaluation Criteria 怎么定义
```

Benchmark 最终测量到什么能力，很大程度上由 Evaluation Criteria 决定。

# 一个错误 Evaluator 的例子

假设我们希望评估：

```text

```

但只有：

```text
cargo test PASS
```

这个条件。

那么 Agent 可以：

```text
删除失败测试
  ->
cargo test
  ->
PASS
```

Evaluator 给出：

```text
1.0
```

但是 Agent 明显没有正确完成任务。

这说明问题不一定只出在 Agent。

还可能是：

```text
Evaluation Criteria
```

不完整。

所以 Evaluation 本身也需要被认真设计。

# Evaluation 也会有 Bug

做 Agent Evaluation 时，很容易只关注：

```text
Agent 为什么失败？
```

但还应该问：

```text
我们的 Evaluator 真的在检查我们关心的东西吗？
```

例如 Rubric：

```text
回答是否专业？
```

就非常模糊。

更好的 Rubric：

```text
1. 是否识别 overlapping mutable borrows
2. 是否解释冲突原因
3. 是否提供有效修复
4. 是否包含错误 Rust 规则
```

Evaluator 越明确：

```text
结果越容易解释
```

Evaluator 越模糊：

```text
分数越难解释
```

# 一次运行不等于真实能力

LLM 输出存在随机性。

同一个 Eval Case：

```text
Run 1 -> PASS

Run 2 -> FAIL

Run 3 -> PASS
```

完全可能发生。

所以真正的 benchmark 通常会：

```text
重复运行
```

例如一种指标关心：

```text
k 次里至少成功一次
```

它更接近：

```text
这个 Agent 有没有能力解决问题？
```

另一种指标关心：

```text
k 次全部成功
```

更接近：

```text
这个 Agent 稳不稳定？
```

这些可以进一步扩展成：

```text
Pass@k
Reliability
```

但这一章不实现完整 Metrics System。

每个 Case 默认只运行一次：

```text
PASS / FAIL
```

这里只需要理解：

> **一次 Agent Run 是 Evaluation 的最小实验单位。**

# Rust 实现要点

这一章真正新增的 Rust 内容并不复杂：

* 从 `s20` 继续使用 `Agent + ToolContext + ToolRouter`。
* 给 Agent 增加非交互式 `run()`。
* 使用 `AgentRun` 返回一次完整执行结果。
* 使用 `Vec<ToolCallRecord>` 保存最小 Observable Trajectory。
* 使用 Fixture 创建可重复 Environment。
* 使用 `EvalCase` 描述 Task、Environment 和 Evaluator。
* 使用 `EvalRunner` 完成 prepare → run → evaluate。
* 使用 `EvalResult` 统一表达评分结果。
* 能程序判断的条件优先 Assertion。
* 无法确定性判断的自然语言质量使用 LLM Judge。
* LLM Judge 使用明确 Rubric，而不是笼统评价。

这一章重点不是新的 Rust 技巧。

而是：

> **开始把 Agent 当成一个可以被实验和测量的系统。**

* Docker Sandbox。
* Multi-model Parallel Evaluation。
* 完整 Pass@k Metrics。

* Production Trajectory 回流。
* 自动生成 Regression Case。

```text

+

+
Agent Run

```

# 本章最重要的四个问题

如果读完这一章，只记住四个问题就够了。

每次想评估一个 Agent 时，先问：

## 1. Task

```text
我到底让 Agent 完成什么？
```

## 2. Environment

```text
每次运行时，
Agent 是不是从同样的状态开始？
```

## 3. Observation

```text
除了最终回答，
我还需要观察哪些真实行为和环境变化？
```

## 4. Evaluation Criteria

```text
什么条件才真正代表成功？
```

最后才决定：

```text
这个条件能直接 assert 吗？
```

如果可以：

```text
Assertion Evaluator
```

如果不可以：

```text
Rubric + LLM Judge
```

这就是设计一个 Agent Eval Case 的基本方法。

# 总结

前面的章节让 Agent：

```text
能够行动
```

这一章开始判断：

```text
它行动得对不对
```

`s21` 从 `s20_tool_refactor` 继续演进。

Agent 本身只做两个很小的变化：

```text
Agent::run()
+
AgentRun / ToolCallRecord
```

真正新增的是 Agent 外面的：

```text
EvalCase
EvalRunner
Evaluator
EvalResult
```

Agent Evaluation 的核心流程并不复杂：

```text
定义 Task
  ->
准备 Environment
  ->
运行 Agent
  ->
观察 Agent Run
  ->
按照 Evaluation Criteria 评分
```

如果成功条件可以直接验证：

```text
Assertion
```

如果无法直接验证：

```text
Rubric
+
LLM-as-a-Judge
```

而一个好的 Eval Case 最关键的不是：

```text
题目有多复杂
```

而是：

> **它有没有清楚定义什么叫成功。**

前二十章主要在回答：

```text
How do we build an agent?
```

从这一章开始，我们加入另一个同样重要的问题：

```text
How do we know it works?
```
