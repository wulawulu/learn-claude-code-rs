# s21: Agent Evaluation

English | [中文](./s21.md)

Earlier chapters ask one question:

> **How do we build a more capable agent harness?**

They progressively add an agent loop, tools, planning, subagents, skills,
context compaction, permissions, memory, recovery, tasks, background work,
teams, worktrees, MCP, and typed tool routing.

Once an agent can do more, a second question becomes just as important:

> **How do we know it actually did the right thing?**

An agent may claim that a task is complete when tests still fail. A prompt
change may look better because one run happened to succeed. An agent may guess
the right answer without using the required evidence, or make tests pass by
deleting them. Open-ended answers may not have one exact expected string.

These are agent evaluation problems.

## Goal

This chapter does not build a complete benchmark platform or reproduce
SWE-bench, GAIA, or tau-bench. Its narrower goal is to implement the smallest
complete evaluation loop:

1. Define an evaluation task.
2. Prepare a repeatable environment.
3. Run the agent and record its observable behavior.
4. Check deterministic assertions where possible.
5. Inspect the tool trajectory when the process matters.
6. Use LLM-as-a-Judge when programmatic checks are insufficient.

The resulting flow is:

```text
Eval Case
   |
   v
Prepare Environment
   |
   v
Run Agent
   |
   v
Agent Run
   |
   +--------------------+
   |                    |
   v                    v
Assertion Evaluator   LLM Judge
   |                    |
   +---------+----------+
             |
             v
         Eval Result
```

## Why Start from s20 Instead of sfull

This chapter evolves directly from `s20_tool_refactor`. That chapter already
provides a small but useful agent:

```text
Agent
├── AgentRuntime
├── ToolContext
└── ToolRouter
```

It also has the tools needed by the evaluation cases:

```text
bash
read_file
write_file
edit_file
```

This is a better subject for an introductory evaluation chapter than `sfull`,
which also includes permissions, compaction, recovery, memory, skills, tasks,
background work, teams, worktrees, MCP, and more. With a smaller subject, a
failure is easier to attribute to the model, tools, harness, environment, or
evaluator.

The evaluated agent should be simple enough to understand, while the
evaluation structure should be explicit.

## The Agent Changes Only Slightly

`s21` does not redesign the agent. It adds two capabilities to the s20 agent:

```text
s20 Agent
   |
   +-- Agent::run()
   |
   +-- AgentRun recording
   |
   v
s21 Agent
```

Most new concepts live outside the agent:

```text
EvalCase
EvalRunner
Evaluator
EvalResult
```

The boundary is intentional: the agent performs a task; the evaluation harness
decides how well it performed.

## Why Ordinary Unit Tests Are Not Enough

A normal unit test has a stable execution path:

```text
fixed input -> fixed function -> fixed output -> assertion
```

An agent can solve the same coding task through different valid paths:

```text
read_file -> edit_file -> bash cargo test -> final answer
```

or:

```text
bash cargo test -> read_file -> edit_file -> bash cargo test -> final answer
```

Requiring an exact sequence of actions would reject valid solutions. Agent
evaluation usually asks broader questions:

- Was the task completed?
- Is the final environment correct?
- Did any forbidden behavior occur?
- Does the answer meet the required quality bar?

The evaluated subject is not one function. It is the system formed by:

```text
Model + Prompt + Tools + Harness + Environment
```

For agents, it is often more accurate to say:

```text
Agent = Model + Harness
```

The same model can behave very differently in a bash-only harness and in one
with file tools, permissions, compaction, recovery, and skills.

## The Evaluation Harness Sits Outside the Agent

The agent should not need to know that it is running inside a benchmark:

```text
+----------------------------------+
|        Evaluation Harness        |
|                                  |
|  prepare environment             |
|          |                       |
|          v                       |
|      +-------+                   |
|      | Agent |                   |
|      +---+---+                   |
|          |                       |
|          v                       |
|      Agent Run                   |
|          |                       |
|          v                       |
|      Evaluator                   |
|          |                       |
|          v                       |
|      Eval Result                 |
+----------------------------------+
```

From the agent's perspective, it simply receives a normal task such as:

```text
Fix the bug in this Rust project.
```

The evaluator does not help find the answer. It prepares the environment, runs
the agent, observes the outcome, and scores it.

## What Is an Eval Case?

A question and an expected answer are enough for simple QA, but an agent can
also modify an environment. A complete agent eval case therefore needs at
least:

```text
Task + Environment + Evaluation Criteria
```

In other words:

1. What must the agent accomplish?
2. What state does it start from?
3. What conditions count as success?

This chapter uses a deliberately small representation:

```rust
pub struct EvalCase {
    pub name: String,
    pub prompt: String,
    pub fixture: Option<PathBuf>,
    pub evaluator: Evaluator,
}
```

The point is the lifecycle, not a sophisticated dataset schema.

### Task

The prompt is the task sent to the agent:

```text
The calculator crate crashes when dividing by zero.

Fix the bug without changing the public function signature.
Run the tests before finishing.
```

An `EvalRunner` acts like an automated user that can present the same task
repeatedly and score the result independently.

### Environment

The task alone is insufficient. If the first run fixes a repository and the
second run reuses it, the two runs no longer start from the same problem.

This chapter resets environments with fixtures:

```text
fixtures/
├── bug_fix/
│   ├── Cargo.toml
│   ├── src/lib.rs
│   └── tests/calculator.rs
└── file_lookup/
    ├── README.md
    ├── config.toml
    └── data.json
```

Before each run, the fixture is copied to a fresh temporary workspace:

```text
fixture -> temporary workspace -> agent
```

This is environment reset, not a security sandbox. The file tools enforce that
paths remain under `ToolContext.work_dir`. The bash tool merely uses that path
as its working directory and can still access anything allowed by the host OS.
Docker, containers, and OS-level isolation are outside this chapter's scope.

### Tools

The environment controls what the agent can see; tools control what it can do.
All three cases use the same model, system prompt, router, and tool set. Only
the task, environment, and evaluation criteria vary:

```text
                  Agent
                    |
       +------------+------------+
       |            |            |
       v            v            v
    bug_fix     file_lookup   rust_explain
```

This demonstrates that one agent can require different evaluation methods for
different kinds of tasks.

## A Programmable Agent Entry Point

The s20 agent is primarily interactive, but an evaluation runner should not
simulate terminal input. It needs a direct API:

```rust
pub async fn run(
    &mut self,
    prompt: impl Into<String>,
) -> anyhow::Result<AgentRun>
```

Both the CLI and evaluator can then reuse the same loop:

```text
           CLI
            |
            v
        Agent::run()
            ^
            |
         EvalRunner
```

## AgentRun and Observable Trajectories

A final claim such as "I fixed the bug and all tests pass" does not prove that
the bug is fixed or that tests were run. Evaluation needs a record of what the
agent actually did:

```rust
pub struct AgentRun {
    pub final_answer: String,
    pub tool_calls: Vec<ToolCallRecord>,
}

pub struct ToolCallRecord {
    pub name: String,
    pub input: serde_json::Value,
    pub output: String,
}
```

A run might record:

```text
read_file("src/lib.rs")
edit_file(...)
bash("cargo test")
test result: ok
final answer
```

This sequence of observable behavior is the trajectory. It may include
assistant messages, tool names, inputs, outputs, the final answer, and—when
needed—environment changes.

Trajectory does not mean hidden chain of thought. An evaluator only needs
observable evidence: what the agent said, which tools it called, their inputs
and outputs, the final environment, and the final answer.

A production system might use traces, spans, JSONL, databases, or
OpenTelemetry. `Vec<ToolCallRecord>` is enough here because the goal is to show
why behavior must be observable, not to build a complete telemetry platform.

## Result Evaluation and Trajectory Evaluation

An `AgentRun` supports two complementary questions:

```text
Result evaluation:     Is the final result correct?
Trajectory evaluation: How did the agent get there?
```

For example, two agents may both make `cargo test` pass:

```text
Agent A: fix src/lib.rs -> cargo test -> PASS
Agent B: delete failing tests -> cargo test -> PASS
```

A final-state check alone may incorrectly reward Agent B. Real evaluations
often need both the final state and the trajectory, including checks for
forbidden side effects.

## Two Basic Evaluators

This chapter implements two evaluator families:

```text
Evaluator
├── Assertion
└── LLM Judge
```

The selection rule is simple:

> Prefer deterministic verification whenever the success condition can be
> checked directly.

Use an LLM judge only when a reliable programmatic check is not available.

## Assertion Evaluator

For a code repair, the evaluator can run the tests itself:

```rust
let output = Command::new("cargo")
    .arg("test")
    .current_dir(&workspace)
    .output()
    .await?;

let passed = output.status.success();
```

The result is independent of the agent's claim:

```rust
EvalResult {
    passed,
    score: if passed { 1.0 } else { 0.0 },
    reason: /* evaluator evidence */,
}
```

If the agent says all tests pass but the evaluator's test command fails, the
case fails. Evaluation turns "the agent says it works" into "we verified that
it works."

Assertions can check much more than a test command:

- whether a file exists or contains expected data;
- whether a command exits successfully;
- whether a JSON field has the expected value;
- whether a tool was called or forbidden;
- whether protected files or directories changed;
- whether a database reached the required state.

A code case might require all of the following:

```text
cargo test passes
AND tests/ is unchanged
AND Cargo.toml still exists
```

## Case 1: SWE-bench-Inspired Code Repair

The first fixture contains a small calculator crate:

```text
fixtures/bug_fix/
├── Cargo.toml
├── src/lib.rs
└── tests/calculator.rs
```

Its implementation panics on division by zero:

```rust
pub fn divide(a: i32, b: i32) -> i32 {
    a / b
}
```

The fixture also contains the desired behavior:

```rust
#[test]
fn divide_by_zero_returns_zero() {
    assert_eq!(divide(10, 0), 0);
}
```

The agent receives:

```text
The calculator crate crashes when dividing by zero.

Fix the bug without changing the public function signature.
Run the tests before finishing.
```

The evaluator does not require a fixed action sequence. After the agent exits,
it independently runs `cargo test` in the modified workspace:

```text
copy fixture -> run agent -> modified workspace -> cargo test -> PASS/FAIL
```

This case demonstrates deterministic evaluation of final environment state.

It can also inspect the trajectory to see whether the agent proactively ran
the tests:

```rust
let ran_tests = run.tool_calls.iter().any(|call| {
    call.name == "bash"
        && call.input.to_string().contains("cargo test")
});
```

That process check is useful, but independent final-state verification remains
more important.

## Case 2: GAIA-Inspired Tool Use

The second fixture is a small information-retrieval workspace:

```text
fixtures/file_lookup/
├── README.md
├── config.toml
└── data.json
```

`data.json` contains:

```json
{
  "services": {
    "service-a": { "timeout": 30 },
    "service-b": { "timeout": 60 }
  }
}
```

The task is:

```text
What is the timeout configured for service-a?

Find the answer from the files in the workspace.
```

The evaluator checks both the final answer and the evidence-gathering action:

```rust
let answer_correct = run.final_answer.contains("30");

let read_data_file = run.tool_calls.iter().any(|call| {
    call.name == "read_file"
        && call.input.to_string().contains("data.json")
});

let passed = answer_correct && read_data_file;
```

If the model guesses `30` without reading the file, the answer is correct but
the case still fails. The actual capability under test is using workspace tools
to retrieve information, not merely producing the expected token.

This illustrates a general state-transition model:

```text
Initial State -> Agent Actions -> Final State
```

An evaluator can inspect the actions, the final state, or both. A successful
case may require the target outcome and the absence of forbidden side effects.

## When Assertions Are Not Enough

Some tasks have many valid answers. Consider:

```text
Explain why this Rust code fails to compile and provide a beginner-friendly
fix.
```

Two answers can use different wording while both correctly explain overlapping
mutable borrows. Exact string equality is inappropriate, and a keyword check
such as `answer.contains("borrow")` can accept incorrect explanations.

This is where LLM-as-a-Judge can help.

## LLM-as-a-Judge and Rubrics

An LLM judge receives:

```text
Task + Agent Answer + Rubric
```

The rubric is the grading standard. "Is this answer good?" is too vague. A
better rubric names concrete criteria:

1. Identify the overlapping mutable borrows.
2. Explain why the borrows conflict.
3. Provide at least one valid fix.
4. Avoid inventing nonexistent Rust rules.
5. Make the explanation understandable to a beginner.

The judge returns structured output such as:

```json
{
  "passed": true,
  "score": 0.9,
  "reason": "The answer identifies the overlapping mutable borrows and provides a valid fix."
}
```

Clear rubrics make judge outcomes more consistent and explainable. The key is
not a complicated judge prompt; it is an explicit definition of success.

## Case 3: Open-Ended Rust Explanation

The third case presents this code directly:

```rust
fn main() {
    let mut values = vec![1, 2, 3];

    let first = &mut values[0];
    let second = &mut values[1];

    *first += 1;
    *second += 1;
}
```

The task asks the agent not to use tools, to explain the borrow error to a Rust
beginner, and to provide at least one valid fix.

The rubric requires the answer to:

- identify overlapping mutable borrows;
- explain that Rust rejects overlapping `&mut` borrows;
- provide at least one valid fix;
- avoid claiming that separate vector elements can never be mutated together;
- remain understandable to a beginner.

The flow is:

```text
Task -> Agent -> Final Answer + Rubric -> LLM Judge -> score + reason
```

## Choosing Between Assertions and a Judge

Use a direct check whenever real state can be inspected reliably:

| Evaluation criterion | Preferred evaluator |
| --- | --- |
| `cargo test` passes | Assertion |
| A file exists | Assertion |
| A JSON value equals `30` | Assertion |
| A tool was called | Assertion |
| A protected path was modified | Assertion |
| Database state is correct | Assertion |
| An explanation is accurate | LLM Judge |
| An answer is complete | LLM Judge |
| Documentation is clear | LLM Judge |
| Advice is reasonable | LLM Judge |

The default order is:

```text
Deterministic verification first -> LLM-as-a-Judge when necessary
```

## EvalResult and Evaluator

Every evaluator returns the same result shape:

```rust
pub struct EvalResult {
    pub passed: bool,
    pub score: f32,
    pub reason: String,
}
```

An assertion may return a score of `1.0`, while an LLM judge may return `0.9`.
The runner does not need to understand how either score was produced.

For this small chapter, an enum is enough:

```rust
pub enum Evaluator {
    Assertion(AssertionEvaluator),
    LlmJudge(LlmJudgeEvaluator),
}
```

Dispatch remains straightforward:

```rust
impl Evaluator {
    pub async fn evaluate(
        &self,
        run: &AgentRun,
        workspace: &Path,
    ) -> anyhow::Result<EvalResult> {
        match self {
            Evaluator::Assertion(evaluator) => {
                evaluator.evaluate(run, workspace).await
            }
            Evaluator::LlmJudge(evaluator) => {
                evaluator.evaluate(run).await
            }
        }
    }
}
```

A plugin registry or dynamic evaluator factory would obscure the core idea:
the same `AgentRun` can be evaluated in different ways.

## EvalRunner

The runner is the composition root for the evaluation lifecycle:

```rust
pub async fn run_eval(case: &EvalCase) -> anyhow::Result<EvalResult> {
    let workspace = prepare_workspace(case)?;
    let mut agent = build_agent(&workspace).await?;
    let run = agent.run(&case.prompt).await?;
    let result = case.evaluator.evaluate(&run, &workspace).await?;
    Ok(result)
}
```

The flow is simply:

```text
prepare -> run -> evaluate
```

In ordinary test terminology, this is Arrange, Act, Assert, except that Act
runs a complete agent rather than one function.

The responsibility boundary is:

```text
EvalRunner                    Agent
├── prepare workspace         ├── receive task
├── create agent              ├── call tools
├── provide task              ├── modify environment
├── collect AgentRun          ├── produce final answer
└── invoke evaluator          └── return AgentRun
```

The agent does not grade itself, and the evaluator does not help solve the
task.

## What the Three Cases Teach

### Case 1: Code Repair

```text

```

Focus: final-state evaluation and deterministic assertions.

### Case 2: Tool-Based Lookup

```text

```

## Why Not Run Full Benchmarks Here?

SWE-bench uses real repositories, issues, agent patches, and test patches. A
complete integration also needs dataset handling, repository checkout, exact
commits, Docker environments, dependency installation, version compatibility,
and a benchmark runner. This chapter borrows only its central idea: let the
agent modify a real environment and independently verify the final state.

GAIA combines questions, tools, information retrieval, web content, files, and
attachments. This chapter reduces that pattern to `question -> read_file ->
answer` so the evaluation mechanics remain visible.

Tau-bench-style systems may include a user simulator, an agent, and an
environment, then evaluate actions, state, and communicated information. This
chapter retains one key lesson: a correct result and a correct process are
different dimensions.

## Evaluation Criteria Define the Real Task

Consider two cases with the same prompt:

```text
Find the timeout of service-a.
```

Evaluator A requires:

```text
Final answer == 30
```

Evaluator B requires:

```text
Final answer == 30 AND read_file("data.json") occurred
```

These are different evaluation tasks because they define success differently.
What a benchmark measures depends heavily on its evaluation criteria, not just
the wording or title of the task.

A weak evaluator can reward undesirable behavior. If a code-repair evaluator
checks only that tests pass, an agent may delete the failing tests. The flaw is
then in the evaluation criteria, not only in the agent.

Evaluators can have bugs too. Vague rubrics such as "Is the answer
professional?" produce hard-to-interpret scores. Explicit criteria make both
failures and improvements easier to understand.

## One Run Does Not Equal Capability

LLM behavior is stochastic. The same case may produce:

```text
Run 1 -> PASS
Run 2 -> FAIL
Run 3 -> PASS
```

Real benchmarks therefore repeat cases. A metric that asks whether at least
one of `k` runs succeeds measures something like potential capability. A
metric that asks whether every run succeeds measures reliability.

This chapter implements neither a full metrics system nor Pass@k. It runs each
case once and reports pass or fail. The important concept is that one agent run
is the smallest experimental unit.

## What Evaluation Enables

With a stable set of cases, experiments become repeatable. You can keep the
harness and dataset fixed while comparing models, or keep the model and dataset
fixed while toggling a harness component:

```text
Compact ON  vs Compact OFF
Old Prompt  vs New Prompt
Old Agent   vs New Agent
```

The component comparison is an ablation. Evaluation replaces "this version
feels better" with a repeatable experiment.

Future cases could target individual `sfull` capabilities:

```text
Compact    -> long-context case
Recovery   -> tool-failure case
Permission -> unsafe-action case
Memory     -> cross-session case
Subagent   -> large-repository case
```

Comparing each component on and off would move from an introduction to
evaluation-driven harness development.

The first twenty chapters mostly build. This chapter adds measurement:

```text
Build -> Evaluate -> Improve -> Evaluate
```

## The Minimal Evaluation Harness

After removing incidental details, the chapter has this structure:

```text
                     +------------------+
                     |    Eval Case     |
                     +---------+--------+
                               |
                               v
                     +------------------+
                     |   Environment    |
                     +---------+--------+
                               |
                               v
                     +------------------+
                     |      Agent       |
                     |  Model + Harness |
                     +---------+--------+
                               |
                               v
                     +------------------+
                     |    Agent Run     |
                     | answer + actions |
                     +---------+--------+
                               |
                  +------------+------------+
                  |                         |
                  v                         v
        +-------------------+     +-------------------+
        | Assertion         |     | LLM Judge         |
        | Evaluator         |     | + Rubric          |
        +---------+---------+     +---------+---------+
                  |                         |
                  +------------+------------+
                               |
                               v
```

The Rust implementation follows directly:

- reuse `Agent`, `ToolContext`, and `ToolRouter` from s20;
- add non-interactive `Agent::run()`;
- return an `AgentRun` with the answer and tool calls;
- copy fixtures into repeatable workspaces;
- describe task, environment, and evaluator with `EvalCase`;
- run prepare, execute, and evaluate through `EvalRunner`;
- normalize outcomes with `EvalResult`;
- prefer assertions for programmatically verifiable conditions;
- use an explicit rubric and LLM judge for open-ended quality.

The important change is not a new Rust technique. It is treating the agent as
a system that can be measured experimentally.

## Out of Scope

This minimal implementation does not include:

- a full SWE-bench runner or GAIA dataset;
- a tau-bench user simulator;
- dataset management or Docker sandboxing;
- parallel multi-model evaluation;
- Pass@k and reliability metrics;
- dashboards or evaluation databases;
- production trajectory ingestion;
- automatic regression-case generation;
- a component ablation framework;
- judge ensembles, calibration, or human evaluation;
- cost and token metrics;
- comprehensive safety evaluation;
- dedicated benchmarks for every `sfull` component.

All of these can grow from the same foundation:

```text
Case + Environment + Agent Run + Evaluator
```

## Where to Go Next

Useful deterministic checks include:

```text
CommandExitCode
FileExists
FileContent
GitDiff
ProtectedPath
ToolCalled
ForbiddenTool
```

Multiple cases can form a dataset. Repeating a case enables Pass@k and
reliability measurements. Running one dataset across models enables model
comparison. Toggling harness features enables ablations. Eventually, the same
evaluation harness can target `sfull` and measure when compaction, recovery,
memory, or subagents actually help.

## Four Questions to Ask

When designing an agent evaluation, start with four questions.

### 1. Task

```text
What exactly must the agent accomplish?
```

### 2. Environment

```text
Does every run begin from the same state?
```

### 3. Observation

```text
Besides the final answer, which behaviors and environment changes matter?
```

### 4. Evaluation Criteria

```text
Which conditions truly represent success?
```

Then decide whether those conditions can be asserted directly. If they can,
use an assertion evaluator. Otherwise, use a clear rubric and an LLM judge.

## Summary

Earlier chapters teach the agent to act. This chapter begins measuring whether
it acts correctly.

The s20 agent gains only `Agent::run()` and observable `AgentRun` /
`ToolCallRecord` values. The main additions sit outside the agent:

```text
EvalCase -> EvalRunner -> Evaluator -> EvalResult
```

The core loop is:

```text
define task
  -> prepare environment
  -> run agent
  -> observe agent run
  -> score against evaluation criteria
```

Use deterministic assertions when the true state can be verified. Use a rubric
and LLM-as-a-Judge when natural-language quality cannot be checked reliably by
code.

A good eval case is not defined by how complicated its prompt is. It is defined
by how clearly it states what success means.

The first twenty chapters ask:

```text
How do we build an agent?
```

This chapter adds an equally important question:

```text
How do we know it works?
```
